# Meeting Workspace Boundaries

本文档定义两个容易混淆、但必须解耦的能力边界：

- `会议工作区`
- `实时语音助手`

二者都消费会议语音，但产品目标、时延要求、输出形态和工程边界不同。

## 一句话定义

`实时语音助手` 是会里的 AI 与会者，负责即时听说与互动。

`会议工作区` 是会里的协作操作台，负责近实时理解、任务编排、执行跟踪和结果沉淀。

## 边界总结

### 实时语音助手

目标：

- 像一个真实成员一样参与讨论
- 对当前问题快速响应
- 支持语音或短文本即时反馈

输入：

- 当前发言音频
- 最近一小段会议上下文
- 主持人或用户的直接提问

输出：

- 实时语音回复
- 短文本回复
- 会议内即时问答

特点：

- 强依赖低时延
- 面向对话体验
- 偏前台交互
- 不负责长流程任务管理

### 会议工作区

目标：

- 将会议内容近实时转成可消费上下文
- 自动提取决策、风险、行动项、待办
- 将轻任务会中派发给 agent 立即执行
- 将重任务沉淀为会后 todo 持续跟踪

输入：

- 近实时语音转写文本
- 会议元数据与成员身份
- 用户手动选择的上下文片段
- agent 执行结果和状态回报

输出：

- context 区结构化内容
- todo / decision / risk / owner / deadline
- agent 任务分解和派发
- output 区执行结果与状态汇报
- 会后沉淀材料

特点：

- 关注秒级近实时，而不是子秒级对话
- 面向工作流推进
- 偏后台协作与执行
- 是会议生产力主系统

## 为什么不能混成一条链路

如果把二者混为一体，会产生三类问题：

- 低时延语音链路和长生命周期任务编排耦合，状态机会迅速失控
- 一条链路故障会同时影响“能不能说”和“能不能干”
- UI 会同时承担成员交互和任务调度，认知负担过高

因此应保持：

- 语音互动链路独立
- 工作区编排链路独立
- 共享 transcript / context，但不共享状态机

## 推荐职责划分

### 实时语音助手负责

- 当前音频的即时理解
- 基于最近上下文进行即时问答
- 语音回复和会内短反馈
- 被点名后的快速响应

### 实时语音助手不负责

- 全会议 transcript 编排
- todo 生命周期管理
- agent 任务队列和调度
- 会后任务沉淀

### 会议工作区负责

- STT 转写接入与 transcript 累积
- context 区维护
- 决策 / 待办 / 风险提取
- 任务拆解、优先级判断、owner 归属
- 通过 agent bridge 派发轻任务
- 跟踪执行状态并在 output 区回报
- 会后待办沉淀

## 典型用户体验

会中发生一段技术讨论后，系统行为应当分成两条并行路径：

1. `实时语音助手`
   - 在被点名时直接回答问题
   - 对当前方案给即时意见

2. `会议工作区`
   - 将语音转写放入 context 区
   - 自动抽取新决策和 todo
   - 识别可立即执行的小任务
   - 通过 agent bridge 派发给本地 agent
   - 在 output 区持续回报执行进展和结果
